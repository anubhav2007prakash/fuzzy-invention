## Reporting a Vulnerability

> **Please do NOT open a public GitHub issue for security vulnerabilities.**
> Doing so exposes users to risk before a fix is available.

### Private Disclosure (Preferred)

Report security vulnerabilities through GitHub's private security advisory
system:

👉 **[Open a Security Advisory](https://github.com/anubhav2007prakash/fuzzy-invention/security/advisories/new)**

This creates an end-to-end encrypted thread visible only to you and the
repository maintainers.

### What to Include

To help us triage and reproduce the issue quickly, please include:

- **Description** — a clear explanation of the vulnerability
- **Type** — e.g. injection, broken authentication, cryptographic weakness,
  data exposure, path traversal, SSRF, etc.
- **Affected component** — backend API, ML pipeline, cryptographic hash chain,
  frontend, CI/CD workflow, supply-chain script
- **Steps to reproduce** — minimal proof-of-concept (do not include live
  exploit code targeting real systems)
- **Potential impact** — confidentiality, integrity, or availability impact;
  CVSS score estimate if possible
- **Suggested fix** (optional)

## Response Timeline

| Event | Target time |
|-------|------------|
| Acknowledgement of report | **72 hours** |
| Initial triage and severity classification | **5 business days** |
| Fix developed and reviewed | **14 days** for High/Critical |
| Coordinated public disclosure | After fix is merged and released |

We follow **coordinated disclosure**: we ask reporters to keep the details
private until a fix is available, and we will credit reporters in the release
notes unless they prefer anonymity.

## Scope

### In scope

The following are in scope for security reports:

- **Backend API** (`backend/app/`) — injection, authentication bypass,
  authorisation flaws, path traversal, unsafe deserialization
- **Cryptographic hash chain** (`backend/app/cryptography/`) — hash collision
  exploits, chain integrity bypass, canonicalization weaknesses
- **ML pipeline** (`backend/app/ml/`) — adversarial data injection, model
  poisoning vectors reachable via the API
- **Failure injection framework** (`backend/tests/failure_injection/`) —
  injectors that could escape test isolation and affect production state
- **Supply-chain workflows** (`.github/workflows/`) — dependency confusion,
  GitHub Actions injection, pinned SHA bypass
- **Frontend** (`frontend/`) — XSS, CSRF, insecure API key handling

### Out of scope

- Theoretical vulnerabilities without a working proof of concept
- Attacks requiring physical access to the server
- Social engineering of maintainers
- Issues in third-party dependencies not directly introduced by this project
  (report those upstream to the respective project)
- Denial-of-service attacks against a publicly hosted demo
- Scanner noise (automated scanner output without manual validation)

## Threat Model Summary

SentinelCrypt AI is a **research prototype**, not a production security
product. The following summarises the intended threat model:

### What the cryptographic ledger protects against

| Threat | Protected? |
|--------|-----------|
| Payload tampering (modifying stored evidence) | ✅ Detected via SHA-256 chain break |
| Record deletion or reordering | ✅ Detected via sequential hash linkage |
| Pointer (`previous_hash`) manipulation | ✅ Detected via chain verification |
| Retrospective alteration of past records | ✅ Invalidates all subsequent hashes |

### What the ledger does **not** protect against

| Threat | Protected? |
|--------|-----------|
| Compromised server administrator | ❌ Admin with DB write access can rebuild the chain |
| Pre-recording manipulation (before anchoring) | ❌ Not detectable |
| Database deletion / availability attacks | ❌ No distributed backup |
| Consensus / Byzantine fault tolerance | ❌ Single-server hash chain only |
| Side-channel attacks | ❌ Out of scope for this prototype |

For the full threat model, see
[docs/security/SENTINELCRYPT_PLATFORM_THREAT_MODEL.md](docs/security/SENTINELCRYPT_PLATFORM_THREAT_MODEL.md).

## Security Hardening Checklist (for deployers)

If you deploy SentinelCrypt AI in any environment beyond local development:

- [ ] Change the `SECRET_KEY` in `.env` to a securely generated random value
- [ ] Enable HTTPS / TLS termination in front of the FastAPI server
- [ ] Restrict database file permissions (SQLite) or use PostgreSQL with
  proper ACLs
- [ ] Do not expose the `/docs` or `/redoc` endpoints publicly
- [ ] Rotate any test keys generated by `scripts/sentinel_verify.py`
- [ ] Review and apply the Content Security Policy for the frontend
- [ ] Enable GitHub's Dependabot for automated dependency alerts
- [ ] Pin all GitHub Actions to their full commit SHA (already done in
  `.github/workflows/`)
